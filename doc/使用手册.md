## 1. CLI 快速开始

### 1.1 基础命令

定制码匠提供三个主要交互模式：

```bash
# 交互式 TUI 模式（推荐日常使用）
code-agent tui

# 带初始提示的 TUI 模式（启动后自动发送提示）
code-agent tui "修复 src/auth.rs 中的空指针异常"

# 非交互式执行模式（适合 CI/CD 和脚本）
code-agent exec "修复 src/auth.rs 中的空指针异常"

# App Server 模式（为 IDE 插件提供后端服务）
code-agent app-server
```

### 1.2 三条命令一分钟上手

```bash
# 1. 检查环境
code-agent doctor
# 输出: ✅ All checks passed.

# 2. 进入项目目录并启动 TUI
cd my-project
code-agent tui

# 3. 开始对话：直接输入你的编码需求
💬 > 帮我给 User 模型添加 created_at 和 updated_at 字段

# 或者启动时直接指定任务
code-agent tui "帮我给 User 模型添加 created_at 和 updated_at 字段"
```

### 1.3 Exec 模式（非交互式）

适合 CI/CD 流水线、Shell 脚本集成、批量处理：

```bash
# 基础用法
code-agent exec "任务描述"

# 指定输出格式
code-agent exec -o json "分析当前项目的依赖关系"

# 使用 Plan 引擎（自动分解任务并并行执行）
code-agent exec --plan "重构 UserService 的缓存逻辑"

# 从 stdin 管道读取任务
echo "检查代码中的 SQL 注入漏洞" | code-agent exec

# 管道输出到文件
code-agent exec "生成项目架构文档" > architecture-report.md
```

**退出码**：

| 退出码 | 含义 |
|--------|------|
| 0 | 任务成功完成 |
| 1 | Agent 执行出错 |
| 2 | 工具调用失败 |
| 3 | 超时 |

### 1.4 配置管理

```bash
# 初始化配置
code-agent config init            # 生成项目级默认配置
code-agent config init --target global  # 生成用户级配置

# 查看配置
code-agent config show            # 显示所有生效配置

# 查看单个配置项
code-agent config get model

# 修改配置
code-agent config set model gpt-4o
code-agent config set timeout_secs 120

# 查看配置路径
code-agent config path
```

### 1.5 环境变量配置

除了配置文件，你也可以通过环境变量快速配置：

```bash
# 必需：API 密钥和模型名称
export LLM_API_KEY="sk-your-api-key"
export LLM_CHAT_MODEL="gpt-4o"

# 可选：API 地址（默认 https://api.openai.com/v1）
export LLM_API_BASE_URL="https://your-custom-api/v1"

# 可选：其他模型
export LLM_EMBEDDING_MODEL="text-embedding-3-small"
export LLM_VL_MODEL="gpt-4o"
```

### 2.5 理解 ReAct 循环（Agent 收到消息后发生了什么？）

当你发送一条消息给 Agent 时，它内部经历了一个叫做 **ReAct 循环**（Reasoning + Acting）的过程。理解这个过程有助于你更好地使用 CraftCoder。

**一次完整的 ReAct 循环包含以下步骤：**

```
你发送消息
    │
    ▼
┌─────────────────────────────────────────────────────┐
│ 1. 思考（Reasoning）                                  │
│    Agent 分析你的问题，决定需要做什么。                  │
│    例如："用户想修复空指针异常，我需要先读取那个文件。"    │
└─────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────┐
│ 2. 行动（Acting）                                     │
│    Agent 调用一个工具来执行操作。                       │
│    例如：read_file("src/auth/login.rs")               │
└─────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────┐
│ 3. 观察（Observing）                                   │
│    Agent 接收工具的执行结果。                           │
│    例如：文件内容被返回给 Agent。                       │
└─────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────┐
│ 4. 判断（Judging）                                     │
│    Agent 判断问题是否已解决：                            │
│    - 如果已解决 → 生成最终回答                          │
│    - 如果未解决 → 回到步骤 1，继续循环                   │
└─────────────────────────────────────────────────────┘
    │
    ▼
你看到最终回答
```

**一个真实的例子：**

```
你: "修复 src/auth/login.rs 中的空指针异常"

Agent 内部循环：
  Turn 1:
    思考 → "我需要先看代码"
    行动 → read_file("src/auth/login.rs")
    观察 → 看到第 42 行 user.getName() 可能为 null
    判断 → "找到问题了，但需要确认调用方"

  Turn 2:
    思考 → "让我看看谁调用了这个方法"
    行动 → grep("user.getName", "src/")
    观察 → 发现 3 处调用都没有做 null 检查
    判断 → "问题已定位，开始修复"

  Turn 3:
    思考 → "添加 null 检查并返回友好错误"
    行动 → edit_file("src/auth/login.rs", ...)
    观察 → 编辑成功
    判断 → "修复完成"

Agent 输出: "已修复第 42 行的空指针异常。添加了 null 检查..."
```

**这对你意味着什么？**

- Agent 可能需要多轮才能完成复杂任务，这是正常的
- 你可以在 TUI 中实时看到 Agent 的思考过程和工具调用
- 如果 Agent 走偏了，你可以随时用 Ctrl+C 中断并纠正它
- 提供清晰的上下文可以减少 Agent 的循环次数

## 3. 代码编辑工作流

### 3.1 标准工作流：生成 → 审查 → 接受/拒绝

定制码匠的代码编辑采用三步确认流程，确保开发者始终拥有最终控制权：

```
┌─────────────┐    ┌─────────────┐    ┌─────────────┐
│ 1. 生成      │ → │ 2. Diff 预览  │ → │ 3. 确认      │
│ AI 分析需求   │    │ 展示变更内容  │    │ 接受/拒绝/修改 │
│ 生成代码     │    │ 逐文件对比    │    │ 一键回滚     │
└─────────────┘    └─────────────┘    └─────────────┘
```

#### 步骤 1：描述需求

```
💬 > 在 UserService 中添加登录失败次数限制，5 分钟内失败 5 次锁定账户 30 分钟
```

#### 步骤 2：审查 Diff

Agent 生成代码后，展示变更的 Diff 预览：

```
📝 变更预览（2 个文件）:

  src/service/UserService.java  (+35 lines, -2 lines)
  src/config/RedisConfig.java   (+12 lines, new file)

  ─── Diff: src/service/UserService.java ───
  + @Autowired
  + private RedisTemplate<String, Integer> redisTemplate;
  +
  + private static final int MAX_ATTEMPTS = 5;
  + private static final int WINDOW_MINUTES = 5;
  + private static final int LOCK_MINUTES = 30;
  +
  + public LoginResult login(String username, String password) {
  +     String key = "login:attempts:" + username;
  +     Integer attempts = redisTemplate.opsForValue().get(key);
  +     ...
```

#### 步骤 3：确认操作

```
操作选项:
  [A] 接受全部变更  [R] 拒绝全部变更  [F] 逐文件审查  [M] 修改后重试
```

### 3.2 支持的文件操作

Agent 通过以下工具操作文件系统：

| 工具 | 功能 | 权限级别 |
|------|------|:---:|
| `read_file` | 读取文件内容（支持指定行范围） | 🟢 低风险 |
| `write_file` | 创建或覆盖文件 | 🟡 中风险 |
| `edit_file` | 精确编辑（search-replace 模式） | 🟡 中风险 |
| `list_dir` | 列出目录内容 | 🟢 低风险 |
| `grep` | 正则表达式搜索文件内容 | 🟢 低风险 |
| `glob` | 文件名模式匹配搜索 | 🟢 低风险 |

### 3.3 Exec 模式下的代码生成

```bash
# 生成代码并直接写入文件（需确认）
code-agent exec "在 src/utils/ 下创建 DateHelper.java 工具类"

# 仅预览变更，不写入文件（Dry Run）
code-agent exec "重构 UserService" --dry-run

# 使用 Plan 引擎自动分解任务
code-agent exec --plan "为所有 Controller 生成单元测试"
```

### 3.4 交互反模式（应避免的操作方式）

| ❌ 不推荐 | ✅ 推荐 |
|-----------|--------|
| "帮我重构整个项目"（目标过大） | "把 UserService 中的缓存逻辑抽取到独立的 CacheService" |
| "修复所有 bug"（范围模糊） | "修复 src/auth/login.rs 中的空指针异常" |
| 一次性提交多个不相关的更改 | 每个独立变更为一个单独请求 |
| 不审查 Diff 直接全部接受 | 逐文件审查，确认每处变更 |

## 4. VS Code 扩展使用

### 4.1 安装

1. 从 VS Code Marketplace 安装或从 `.vsix` 文件手动安装
2. 确保 `code-agent` CLI 已安装并可用
3. 打开任意项目文件夹

### 4.2 核心功能

| 功能 | 触发方式 | 说明 |
|------|----------|------|
| **Agent 对话** | 侧边栏（Cmd+Shift+P → CraftCoder: Open Chat） | 在侧边栏与 Agent 对话 |
| **内联编辑** | 选中代码 → Cmd+K → 输入自然语言指令 | 选中代码后直接描述修改需求 |
| **智能补全** | 输入时自动触发 | 内联幽灵文本，Tab 键接受 |
| **Bug 修复** | 右键菜单 → "CraftCoder: Explain & Fix" | 选中错误代码，自动分析并修复 |
| **文档生成** | 右键菜单 → "CraftCoder: Generate Docs" | 为当前函数/类生成文档注释 |
| **测试生成** | 右键菜单 → "CraftCoder: Generate Tests" | 为当前函数生成单元测试 |

### 4.3 侧边栏对话

VS Code 侧边栏中的 Agent 对话面板支持：

- 多轮对话（保留上下文）
- 流式输出（实时显示 Agent 推理过程）
- Diff 预览（变更在编辑器中高亮显示）
- 一键接受/拒绝变更
- 工具调用可视化（正在读取文件、执行 Shell 等）

### 4.4 配置

在 VS Code 设置（`settings.json`）中可配置：

```json
{
  "craftcoder.appServer.path": "code-agent",
  "craftcoder.completion.enabled": true,
  "craftcoder.completion.delay": 300,
  "craftcoder.telemetry.enabled": false
}
```

## 5. Web API 使用

### 5.1 多用户认证（可选）

Web API 支持轻量级的多用户认证。通过配置文件设置 API Key → 用户标识（UserId）的映射：

```toml
# config.toml
# API Key 认证配置（空 = 匿名模式，所有请求视为同一用户）
[auth]
api_keys = [
    { key = "sk-admin-xxxx", user_id = "admin" },
    { key = "sk-dev-xxxx", user_id = "developer-1" },
]
```

请求时在 HTTP 头中携带 API Key：

```bash
curl -X POST http://localhost:8080/threads \
  -H "Authorization: Bearer sk-admin-xxxx" \
  -H "Content-Type: application/json"
```

- 未配置 API Key 或未携带认证头 → 匿名模式（向后兼容）
- 携带有效 API Key → 线程自动绑定对应用户
- 用户只能看到自己创建的线程

### 5.2 启动 Web API 服务

```bash
# 启动 Web API 服务（独立二进制）
code-agent-web

# 或通过 cargo 直接运行
cargo run --release -p code-agent-web

# Docker Compose 方式启动
cd code-agent-rs
docker compose up -d
```

Web API 服务默认监听 `0.0.0.0:8080`（源码编译）或 `0.0.0.0:3000`（Docker Compose），提供 REST + SSE 接口。

### 5.3 API 端点

| 方法 | 路径 | 说明 | 认证 |
|------|------|------|------|
| `POST` | `/threads` | 创建新线程 | 可选 |
| `GET` | `/threads` | 列出当前用户的所有线程 | 可选 |
| `GET` | `/threads/:id` | 获取线程详情 | 可选 |
| `DELETE` | `/threads/:id` | 删除线程 | 可选 |
| `POST` | `/threads/:id/turns` | 提交用户消息，返回 SSE 事件流 | 可选 |
| `GET` | `/threads/:id/events` | 获取线程历史事件流（SSE） | 可选 |
| `GET` | `/health` | 健康检查 | 无 |
| `GET` | `/` | 静态文件服务（React SPA 管理面板） | 无 |

### 5.4 使用示例

#### 健康检查

```bash
curl http://localhost:8080/health
# 响应: {"status": "ok"}
```

#### 创建线程

```bash
curl -X POST http://localhost:8080/threads \
  -H "Content-Type: application/json" \
  -d '{"title": "斐波那契数列生成器"}'
# 响应: {"thread_id": "thr_abc123", "title": "斐波那契数列生成器", ...}
```

#### 提交对话并流式获取结果（SSE）

```bash
curl -X POST http://localhost:8080/threads/thr_abc123/turns \
  -H "Content-Type: application/json" \
  -d '{"messages": [{"role": "user", "content": "用 Rust 写一个斐波那契数列生成器"}]}'

# SSE 事件流响应:
# event: message_delta
# data: {"content": "我来写一个斐波那契数列生成器..."}
#
# event: tool_call
# data: {"name": "write_file", "arguments": {"path": "src/fib.rs"}}
#
# event: turn_complete
# data: {"final_message": "已生成斐波那契数列生成器，代码在 src/fib.rs"}
```

#### 列出所有线程

```bash
curl http://localhost:8080/threads
# 响应: {"threads": [{"thread_id": "thr_abc123", "title": "...", ...}]}
```

#### JavaScript/TypeScript 客户端示例

```typescript
// 创建线程
const thread = await fetch('http://localhost:8080/threads', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ title: '生成斐波那契数列' }),
});
const { thread_id } = await thread.json();

// SSE 流式对话
const response = await fetch(`http://localhost:8080/threads/${thread_id}/turns`, {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({
    messages: [{ role: 'user', content: '用 Rust 写一个斐波那契数列生成器' }],
  }),
});

const reader = response.body.getReader();
const decoder = new TextDecoder();

while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  
  const text = decoder.decode(value);
  // 解析 SSE 事件...
  console.log('收到:', text);
}
```

### 5.5 SSE 事件类型

Web API 通过 Server-Sent Events（SSE）协议推送实时事件流。以下为所有 SSE 事件类型及数据结构：

| 事件类型 | 方向 | 说明 | 关键字段 |
|----------|------|------|----------|
| `turn_started` | 服务端→客户端 | 轮次开始 | `turn_id`: 本轮次唯一标识 |
| `agent_message_delta` | 服务端→客户端 | Agent 文本增量（流式） | `content`: 流式文本片段 |
| `tool_call_begin` | 服务端→客户端 | 工具调用开始 | `name`: 工具名称, `arguments`: 调用参数, `call_id`: 调用标识 |
| `tool_call_end` | 服务端→客户端 | 工具调用结束 | `call_id`: 对应调用标识, `result`: 执行结果 |
| `token_usage` | 服务端→客户端 | Token 用量统计 | `input_tokens`: 输入 Token, `output_tokens`: 输出 Token |
| `turn_complete` | 服务端→客户端 | 轮次完成 | `turn_id`: 轮次标识, `final_message`: 最终回复 |
| `error` | 服务端→客户端 | 执行错误 | `code`: 错误码, `message`: 错误描述 |

**SSE 事件流格式示例：**

```
event: turn_started
data: {"turn_id": "turn_abc123"}

event: agent_message_delta
data: {"content": "我来分析一下这个需求。首先需要查看当前代码结构..."}

event: tool_call_begin
data: {"name": "read_file", "arguments": {"path": "src/main.rs"}, "call_id": "call_001"}

event: tool_call_end
data: {"call_id": "call_001", "result": "fn main() {\n    println!(\"Hello\");\n}"}

event: agent_message_delta
data: {"content": "代码结构已了解。现在开始编写实现。"}

event: tool_call_begin
data: {"name": "write_file", "arguments": {"path": "src/fib.rs", "content": "..."}, "call_id": "call_002"}

event: tool_call_end
data: {"call_id": "call_002", "result": "文件写入成功"}

event: token_usage
data: {"input_tokens": 1240, "output_tokens": 356}

event: turn_complete
data: {"turn_id": "turn_abc123", "final_message": "已完成斐波那契数列生成器的编写。"}
```

**客户端消费 SSE 的要点：**

- **连接保持**：一次 `POST /threads/:id/turns` 请求对应一次完整的 Agent 执行周期，事件流持续到 `turn_complete` 或 `error` 事件。
- **并发限制**：同一线程同时只能有一个活跃的 turn。需要在 `turn_complete` 后发起下一次请求。
- **断线重连**：SSE 连接中断后，可通过 `GET /threads/:id/events` 获取历史事件重新同步状态。
- **事件顺序**：事件按执行顺序严格排列。`tool_call_begin` 和 `tool_call_end` 成对出现，之间可能嵌套多层。
- **增量渲染**：`agent_message_delta` 事件携带部分文本，客户端应累加拼接以展示完整消息。

### 5.6 团队协作

Web API 支持团队成员间的线程共享和协作。通过 API Key 区分用户身份，在线程级别实现权限管控。

#### 5.6.1 线程共享 API

| 方法 | 路径 | 说明 | 认证 |
|------|------|------|:---:|
| `POST` | `/threads/:id/share` | 将线程共享给指定用户 | 必需 |
| `DELETE` | `/threads/:id/share/:user_id` | 取消对某用户的共享 | 必需 |
| `GET` | `/shared-threads` | 列出其他用户共享给自己的线程 | 必需 |

#### 5.6.2 共享线程

```bash
# 将线程 thr_abc123 共享给 alice（编辑权限）
curl -X POST http://localhost:8080/threads/thr_abc123/share \
  -H "Authorization: Bearer sk-admin-xxxx" \
  -H "Content-Type: application/json" \
  -d '{
    "user_id": "developer-alice",
    "permission": "edit"
  }'

# 响应: {"thread_id": "thr_abc123", "shared_with": "developer-alice", "permission": "edit"}
```

#### 5.6.3 权限级别

| 级别 | 值 | 允许的操作 |
|------|-----|-----------|
| **只读** | `read` | 查看线程内容和历史消息，不可追加对话 |
| **编辑** | `edit` | 在只读基础上，可追加新对话（发起 turn） |
| **管理** | `admin` | 完全控制：追加对话、管理共享、删除线程 |

权限遵循"最小权限原则"：默认不共享，仅在所有者显式授权后他人方可访问。

#### 5.6.4 查看共享线程

```bash
# alice 查看其他人分享给她的线程
curl http://localhost:8080/shared-threads \
  -H "Authorization: Bearer sk-dev-001"

# 响应:
# {
#   "shared_threads": [
#     {
#       "thread_id": "thr_abc123",
#       "owner": "admin",
#       "permission": "edit",
#       "thread_title": "斐波那契数列重构"
#     }
#   ]
# }
```

#### 5.6.5 取消共享

```bash
curl -X DELETE http://localhost:8080/threads/thr_abc123/share/developer-alice \
  -H "Authorization: Bearer sk-admin-xxxx"

# 响应: {"status": "unshared", "thread_id": "thr_abc123", "user_id": "developer-alice"}
```

#### 5.6.6 审计追踪

所有协作操作自动记录到 `audit_log` 表（存储于 `sessions.db`），可追溯每条共享、权限变更和线程访问记录。

通过 SQLite 查询审计事件：

```bash
# 查看某用户的所有操作
sqlite3 sessions.db \
  "SELECT timestamp, action, resource, detail 
   FROM audit_log 
   WHERE user_id = 'developer-alice' 
   ORDER BY timestamp DESC 
   LIMIT 20;"

# 查看某线程的共享历史
sqlite3 sessions.db \
  "SELECT timestamp, user_id, action, detail 
   FROM audit_log 
   WHERE resource = 'thr_abc123' AND action LIKE 'share_%' 
   ORDER BY timestamp;"
```

审计事件类型包括：`thread_create`、`thread_delete`、`share_grant`、`share_revoke`、`tool_call`、`permission_change` 等。

- 支持输入 Token、输出 Token、合计三个维度的展示

| **API Key** | Web API 认证密钥 | 在侧边栏底部单独配置 |

## 9. 自定义工具开发

CraftCoder 提供完整的自定义工具 SDK，开发者可以通过实现标准化的 `Tool` trait 为 Agent 扩展新能力。

### 9.1 一键脚手架

使用 `code-agent tool new` 命令快速创建一个自定义工具项目：

```bash
# 创建新的工具项目
code-agent tool new my-web-search

# 输出:
# ✅ Created project: my-web-search/
#    ├── Cargo.toml
#    ├── src/
#    │   └── lib.rs         # Tool trait 实现模板
#    └── README.md
```

脚手架自动生成标准的 Rust Cargo 项目，包含：
- 完整的 `Tool` trait 实现模板（`name()`、`description()`、`input_schema()`、`capability()`、`execute()`）
- 预配置的 `Cargo.toml`（包含 `code-agent-core` 和 `code-agent-protocol` 依赖）
- 示例单元测试

### 9.2 构建与加载

```bash
# 进入项目目录，编译工具
cd my-web-search
cargo build --release

# 编译产物: target/release/libmy_web_search.so (Linux/macOS)
#            target/release/my_web_search.dll (Windows)

# 方式一：通过配置文件加载
# 在 ~/.config/code-agent/config.toml 中添加：
# [plugins.my-web-search]
# type = "custom"
# path = "target/release/libmy_web_search.so"
# enabled = true

# 方式二：程序化加载（在自定义启动代码中）
# use my_web_search::WebSearchTool;
# registry.register(Arc::new(WebSearchTool::new()))?;
```

工具加载后，Agent 自动发现并通过标准的工具调用接口使用它。

### 9.3 工具开发快速示例

```rust
use async_trait::async_trait;
use code_agent_core::tools::{
    Tool, ToolError, tool_success, require_string,
};
use code_agent_protocol::{CapabilityLevel, ToolResultMessage};

struct GreetTool;

#[async_trait]
impl Tool for GreetTool {
    fn name(&self) -> &str { "greet" }
    fn description(&self) -> &str { "向指定用户打招呼。" }
    fn input_schema(&self) -> serde_json::Value {
        serde_json::json!({
            "type": "object",
            "properties": {
                "name": { "type": "string", "description": "用户姓名" }
            },
            "required": ["name"]
        })
    }
    fn capability(&self) -> CapabilityLevel { CapabilityLevel::Read }
    async fn execute(&self, params: serde_json::Value) -> Result<ToolResultMessage, ToolError> {
        let name = require_string(&params, "name")?;
        Ok(tool_success("", format!("你好，{name}！")))
    }
}
```
